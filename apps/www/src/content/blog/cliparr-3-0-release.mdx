Version 3.0 so soon after v2? That's right!

New features, "breaking" changes, and boring things that will make Cliparr more stable long term and ensure easier and more frequent maintenace.

Just like last time, the change to Cliparr's major version number is driven by [semantic versioning](https://semver.org/).
Since the last update (2.0.2), we've incorporated a few changes that are _technically_ "breaking" changes but are unlikely to impact anyone using Cliparr today.

## What's new

### Choose video, GIF, or audio

The updated export UI starts with a more deliberate choice of **Video**, **GIF**, or _now **Audio**_, with formats and settings tailored to each one. Your format selections are remembered when you switch export types.

**New audio-only exports** are perfect for soundboards, podcasts, sound bites for streamers, and more.

More settings now use smarter defaults based on the original media, and the export screen prevents you from choosing unsupported or incompatible options.

### Fully customizable subtitle tracks

Subtitles are now **fully customizable and independent of your source media**. Freely add, edit, or remove captions, whether the original video includes subtitles or not.

Add your own captions and adjust their text, timing, and styling to suit your clip.

Until now, if you had Cliparr already open and changed the media on your server, you would often need to refresh the dashboard manually for the changes to appear. Not anymore! Plex and Jellyfin now broadcast changes to Cliparr for live updates. The refresh button in the dashboard has been removed.

This change was not free, however.

While it's a small quality-of-life improvement for users, it required more setup in the Cliparr server to receive those updates and relay them to the Cliparr frontend.

This is a clean update, but if we ever want to make Cliparr a fully browser-based application with no server, this is something we'll need to address. Receiving and relaying these updates is now one of the two main reasons the Cliparr server exists. The other is acting as a proxy to handle CORS issues and support a variety of deployment setups. Otherwise, the server remains a thin wrapper.

### Versioned metadata JSON

Exported video and audio clips retain embedded metadata that links them to their source. Currently, this includes movie titles or TV series, season, and episode details when available, as well as the clip's original start time, end time, and duration.

Cliparr writes standard metadata tags where the selected output format supports them, improving compatibility with existing tools. It also embeds a custom JSON tag containing source details and clip timing. This format is a little easier to work with in modern tools and provides a more predictable structure. As far as I know, no other tools consume it yet.

New in v3.0.0, that existing JSON metadata is now **versioned**, with source details and clip timing organized separately.
An explicit version should give developers more confidence when building tools that use Cliparr's metadata. It's one more way Cliparr is maturing.

Here's a simplified example for a 30-second clip from a TV episode:

```json
{
  "version": 1,
  "source": {
    "itemType": "episode",
    "title": "Example episode",
    "showTitle": "Example series",
    "seasonNumber": 1,
    "episodeNumber": 3
  },
  "clip": {
    "sourceStartSeconds": 65.125,
    "sourceEndSeconds": 95.125,
    "durationSeconds": 30
  }
}
```

The timestamps refer to the selected interval in the original source.

**For developers:** Version 1 replaces the previous unversioned `clpr` JSON payload. If you have scripts that read it, update them for the new structure. See the [export metadata documentation](/docs/export-metadata/) for the schema and container-specific tags.

### Performance and security updates

Finally, the boring stuff.

Most of Cliparr's media processing happens in the browser, but security still matters. AI helped identify areas to harden, and this release includes security fixes and dependency updates.

We added several new encoders when adding support for audio exports. So, we took that opportunity to ensure all encoders are lazy-loaded at export, only if they are selected. This might mean a tiny delay before the export button is available, but will reduce overall bandwidth and memory usage.

CI tests and Docker builds are finally significantly faster. We now more intelligently skip certain aspects of the CI workflow when they are not relevant to the changes.
